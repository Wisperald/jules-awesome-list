# Архитектура

## Краткий вывод

Однонаправленный поток данных поверх TDLib: `TelegramClient` превращает JNI-колбэки в
`SharedFlow`, репозитории поддерживают локальное зеркало состояния и публикуют
`StateFlow`, ViewModel'и адаптируют его под экраны, Compose рисует. Внедрение
зависимостей — вручную (`AppContainer`), без кодогенерации.

---

## 1. Слои

```
┌──────────────────────────────────────────────────────────────┐
│  ui/            Compose for TV: экраны, компоненты, тема      │
│                 ViewModel — только адаптация состояния        │
├──────────────────────────────────────────────────────────────┤
│  data/          Репозитории: auth, chats, messages,           │
│                 files, users, settings                        │
├──────────────────────────────────────────────────────────────┤
│  td/            TelegramClient, TdConfiguration, TdException, │
│                 TdLibLoader — единственное место, где виден   │
│                 org.drinkless.tdlib                           │
├──────────────────────────────────────────────────────────────┤
│  TDLib (C++ / JNI)                                            │
└──────────────────────────────────────────────────────────────┘
```

Зависимости направлены строго вниз. `ui/` не импортирует `org.drinkless.tdlib` нигде,
кроме `SettingsViewModel` (запросы статистики хранилища) — это осознанное исключение,
чтобы не заводить репозиторий ради двух вызовов.

---

## 2. Поток обновлений

TDLib доставляет апдейты на собственном JNI-потоке, который **нельзя блокировать**.

```
TDLib JNI thread
      │  Client.ResultHandler
      ▼
Channel(UNLIMITED)        ← trySend, никогда не блокирует и не теряет
      │
      ▼  корутина в applicationScope
MutableSharedFlow<TdApi.Object>
      │
      ├─► AuthRepository     — UpdateAuthorizationState
      ├─► ChatRepository     — UpdateNewChat / ChatPosition / ChatLastMessage / …
      ├─► UserRepository     — UpdateUser / UpdateUserStatus
      ├─► MessageRepository  — UpdateNewMessage / MessageContent / DeleteMessages
      └─► FileRepository     — UpdateFile
```

Небуферизованный `SharedFlow` здесь был бы ошибкой: медленный подписчик остановил бы
поток TDLib. Неограниченный канал переносит задержку на сторону приложения.

## 3. Запросы

`TelegramClient.send()` — `suspendCancellableCoroutine` поверх
`Client.send(query, resultHandler)`:

* `TdApi.Error` превращается в `TdException` с кодом и описанием;
* `send` бросает исключение, `sendOrNull` возвращает `null`, `sendAndForget` игнорирует
  результат (для `ViewMessages`, `OpenChat`, `CloseChat`);
* код `404` — не ошибка, а «список закончился»: так `LoadChats` сообщает о конце.

Запросы конструируются через конструктор без аргументов и присваивание полей
(`request.chatId = …`), а не через позиционный конструктор. TDLib регулярно добавляет и
переставляет параметры между версиями; присваивание по имени переживает такие изменения,
а позиционный конструктор — нет. Ровно так же поступает официальный Java-пример TDLib.

Это не спасает от переименования самих полей: `DraftMessage.inputMessageText` в актуальной
схеме стал `content: DraftMessageContent`. Такие расхождения ловит
`tools/verify-tdlib-api.sh` — компиляция кода против `TdApi`, сгенерированного из
настоящего `td_api.tl`.

## 4. Список чатов

TDLib не отдаёт готовый список. Он присылает чаты по одному (`UpdateNewChat`) и отдельным
потоком — их позиции (`UpdateChatPosition`, поле `positions` в других апдейтах).
`ChatRepository` хранит:

* `chatById: Map<Long, TdApi.Chat>` — объекты чатов, мутируемые на месте;
* `mainListOrder: Map<Long, ChatPosition>` — порядок только для `ChatListMain`.

После каждого значимого апдейта список пересобирается и сортируется по `order`
(TDLib уже закодировал в нём закрепление). Чат без позиции в главном списке из выдачи
исчезает — именно так TDLib сообщает об архивации.

---

## 5. История сообщений

`GetChatHistory` намеренно ленив: первый вызов для «холодного» чата может вернуть пустой
список, пока сообщения тянутся с сервера. `MessageRepository.history()` повторяет запрос
один раз, прежде чем сообщить «дальше ничего нет».

Сообщения хранятся **от новых к старым** — в том же порядке, в котором их отдаёт TDLib, и
в том, который нужен `LazyColumn(reverseLayout = true)`: индекс 0 — нижний пузырь на
экране, подгрузка старых сообщений — простое добавление в конец списка.

Отправка оптимистична: `SendMessage` сразу возвращает сообщение с временным id, оно
вставляется в список, а `UpdateMessageSendSucceeded` заменяет его на постоянное.

## 6. Файлы

| Что | Как |
| --- | --- |
| Аватары, превью | `DownloadFile(synchronous = true)` — корутина ждёт готовый файл |
| Видео, документы | `DownloadFile(synchronous = false)` + подписка на `UpdateFile` |

Синхронная загрузка избавляет от отслеживания прогресса там, где он не нужен; крупные
файлы показывают полосу загрузки и только затем открываются в ExoPlayer.

**Известное ограничение:** файл проигрывается только после полной загрузки. Потоковое
воспроизведение частично загруженного файла потребовало бы собственного
`androidx.media3.datasource.DataSource` поверх растущего локального файла TDLib.

## 7. Авторизация

Состояние принадлежит TDLib целиком: клиент только отвечает на текущий шаг.
`AuthRepository` переводит `TdApi.AuthorizationState` в `AuthStage` — набор, который
понимает UI, включая локальные отказы (`NativeLibraryMissing`, `MissingCredentials`).

По умолчанию предлагается вход по QR-коду (`RequestQrCodeAuthentication`): это
единственный способ войти в Telegram, не набирая номер и код на пульте.

После `LogOut` TDLib закрывает клиент безвозвратно — состояние `Closed` обрабатывается
пересозданием `Client` и повторным `GetAuthorizationState`.

## 8. Навигация и фокус

`TvGramNavGraph` следит за `AuthStage` и сбрасывает back stack при смене авторизации:
выход из аккаунта (в том числе инициированный с другого устройства) всегда приводит на
экран входа, не оставляя за собой открытых чатов.

Все интерактивные элементы построены на одном примитиве — `TvSurface` (Compose
Foundation: `focusable` + `clickable` + `onFocusChanged`), а не на `Surface` из
`tv-material3`. Причина прагматичная: фокус выглядит одинаково на всех экранах —
светлее, с рамкой и чуть крупнее, — а это единственная подсказка, читаемая с трёх метров.

---

## 9. Чего здесь нет

Осознанно не реализовано: секретные чаты, звонки, редактирование и удаление сообщений,
отправка медиа, стикер-паки (в том числе анимированные `.tgs`), опросы, папки чатов,
push-уведомления. Для каждого неподдержанного типа контента показывается понятная
заглушка, а не пустой пузырь.
